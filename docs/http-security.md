# HTTP Security Boundary

This document describes the reusable HTTP security building blocks in
`server/http/security/`. They are intentionally not mounted by this change:
`server/http/app.ts` is outside Agent 4's scope. A later integration change
must compose these handlers with authentication and RBAC middleware.

## Origin and CORS policy

`createOriginPolicy` accepts exact HTTP(S) origins only. `*`, credentials in an
origin, paths, and malformed origins are rejected. `createCorsMiddleware`

- reflects an allowed origin exactly and never emits `Access-Control-Allow-Origin: *`;
- supports credentials for cookie sessions;
- rejects a present but untrusted `Origin` with `403 ORIGIN_NOT_ALLOWED`;
- validates preflight methods and requested headers; and
- allows same-origin/non-browser requests that do not send an `Origin` header.

Local development, Vercel Preview, and Vercel Production must be separate
explicit entries. Preview deployments must be supplied as exact configured
URLs (or an explicitly bounded allow-list generated by deployment tooling).
Never allow every `*.vercel.app` deployment: that would trust unrelated Vercel
projects.

Example integration configuration:

```ts
const origins = createOriginPolicy({
  allowedOrigins: [
    "http://localhost:3000",
    "https://energy-monitor.example.com"
  ],
  allowedPreviewOrigins: [
    "https://energy-monitor-git-feat-web-v3.vercel.app"
  ]
});
app.use(createCorsMiddleware(origins));
```

The existing `APP_ORIGIN` value can supply the production/local entry, but a
future config change should represent multiple explicit origins rather than
silently broadening one origin to a wildcard.

## Cookies

`cookies.ts` provides serialization, parsing, append, and clear helpers without
adding a cookie dependency. The defaults are:

- session cookie `em_session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, and
  `Secure` in production;
- CSRF cookie `em_csrf`: readable by the browser so a same-origin client can
  copy it into a custom header, but still `SameSite=Lax`, `Path=/`, and
  `Secure` in production; and
- no `Domain` attribute, which keeps cookies host-only.

`SameSite=None` is accepted only when `Secure` is also enabled. The production
session token must be generated and stored server-side as a hash; these helpers
do not persist or log raw session tokens.

## CSRF strategy

`createCsrfMiddleware` protects `POST`, `PUT`, `PATCH`, and `DELETE` by default.
It uses a stateless signed double-submit token:

1. the server issues `em_csrf` with `issueCsrfCookie`;
2. the client reads that non-HttpOnly CSRF cookie and sends the same value in
   `X-CSRF-Token`;
3. the server compares the cookie and header in constant time and verifies the
   HMAC; and
4. when a session cookie exists, the signature is bound to that session token.

This does not require process-local state, so it works across Vercel
invocations. The CSRF secret is server-only and must be at least 32 characters.
The login/bootstrap flow should issue an anonymous-bound token first, while
authenticated mutations should issue or rotate a session-bound token after
login/session rotation. Do not exempt mutations merely because `SameSite` is
enabled. CORS/origin validation remains a second, independent check.

## Request metadata

`sanitizeRequestMetadata` produces bounded, log-safe metadata:

- request IDs are limited to the existing safe character set, otherwise a new
  UUID is generated;
- user-agent text is length-limited and control characters are removed;
- origin and referer are reduced to valid HTTP(S) origins; and
- IP values are accepted only when parsed by Node's IP validator.

`trustProxy` must be enabled only when the deployment proxy is known to replace
or sanitize forwarding headers. With `trustProxy: false`, the socket address is
used and client-supplied `X-Forwarded-For` is ignored. Never log cookies,
authorization headers, passwords, CSRF tokens, or database URLs.

## Rate limiting

`RateLimitStore` is the durable boundary. `createRateLimitMiddleware` emits
`RateLimit-*`, `Retry-After`, and a generic `429 RATE_LIMITED` response.

`InMemoryRateLimitStore` is explicitly development/test-only. It is
deterministic and has an injectable clock for tests, but it is process-local and
does not protect a horizontally scaled or serverless deployment.

`PostgresRateLimitStore` is the durable strategy. It hashes the logical key
before storage and performs an atomic bucket upsert. It expects this table to be
created by a later, separately reviewed migration (no migration is added by
Agent 4):

```sql
create table public.http_rate_limit_buckets (
  key_hash text not null,
  window_start timestamptz not null,
  hit_count integer not null check (hit_count > 0),
  primary key (key_hash, window_start)
);
create index http_rate_limit_buckets_expiry_idx
  on public.http_rate_limit_buckets (window_start);
```

The cleanup job should delete buckets older than the longest configured window.
The runtime PostgreSQL role needs only `SELECT`, `INSERT`, `UPDATE`, and
cleanup-specific `DELETE` on this table; migration/admin credentials must remain
separate. On Vercel, use the Supabase transaction pooler for runtime connections
where appropriate and keep migrations on the direct/admin path. The current
Node PostgreSQL query style uses no named prepared statements, which is
compatible with transaction pooling.

## Integration contract and security decisions

The future integration point should be ordered approximately as:

```text
request metadata -> origin/CORS -> rate limit -> CSRF -> session auth -> RBAC -> route/service
```

Authentication endpoints must be reviewed individually. Login may use the
anonymous CSRF token; logout, password changes, user management, settings, and
operational writes require the normal mutation protection. The final route
composition must also preserve the existing `READ_ONLY_MODE` guard: an
authenticated admin must not bypass it.

This Agent 4 change deliberately does not alter `app.ts`, authentication,
sessions, RBAC, migrations, database grants/RLS, package files, or deployment
configuration. Those remain separate reviewable changes.
